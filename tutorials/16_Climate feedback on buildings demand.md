## Climate feedback on buildings demand (feedback loop 1)

This note describes the optional feedback from climate to buildings energy demand.
Heating and cooling degree days (HDD/CDD) scale the climate-sensitive part of
household (`HOU`) and services (`SE`) demand. It applies only to the `technology`
realization of `02_Industry`.

## 1. Switch

In `main.gms`:

```
$setglobal climFeedback off   !! on / off: degree-day feedback on buildings demand
```

or on the command line: `gams main.gms --climFeedback=on ...`.

* `off`: the two equations are compiled exactly as before, so results are identical
  to a model without the feedback.
* `on`: the climate factors are compiled into the equations. With the neutral
  default inputs (ratios = 1, shares = 0) every factor is exactly 1 and results
  are unchanged.

## 2. Method

Buildings demand is recursive: this year = last year × growth factors. A climate
index is built per country, subsector and year:

```
ClimIdx(HDD,t) = 1 + ShHeat * (DD(HDD,t) ^ ElDD(HDD) - 1)
ClimIdx(CDD,t) = 1 + ShCool * (DD(CDD,t) ^ ElDD(CDD) - 1)
```

`DD(·,t)` is the degree-day ratio to 2023 and `ClimIdx = 1` outside the projection
years (`An`), so 2023 and all historical/calibration years are unaffected.

One multiplicative factor is added to each equation in
`modules/02_Industry/technology/equations.gms`, right after the lagged term:

| Equation | Variable | Factor |
|---|---|---|
| `Q02DemSubUsefulSubsec` | `V02DemSubUsefulSubsec` (heating etc.) | `ClimIdx(HDD,t) / ClimIdx(HDD,t-1)` |
| `Q02UsefulElecNonSubIndTert` | `V02UsefulElecNonSubIndTert` (incl. cooling) | `ClimIdx(CDD,t) / ClimIdx(CDD,t-1)` |

Because the equations are recursive, the year-on-year ratio makes the effect
cumulative: after `n` years the demand level carries `ClimIdx(t)/ClimIdx(2023)`,
with no double counting. The factor is 1 when the lagged index is 0.

## 3. Parameters (`02_Industry/technology`)

| Parameter | Meaning | Default |
|---|---|---|
| `DDTYPE` | set `/HDD, CDD/` | |
| `i02ClimDD(DDTYPE,allCy,YTIME)` | degree-day ratio to 2023 (1) | 1 |
| `i02ShHeat(allCy,DSBS)` | space-heating share of `V02DemSubUsefulSubsec` (1) | 0 |
| `i02ShCool(allCy,DSBS)` | cooling share of `V02UsefulElecNonSubIndTert` (1) | 0 |
| `i02ElDD(DDTYPE)` | elasticity of demand to degree days (1) | HDD 1, CDD 1 |
| `i02ClimIdx(allCy,DSBS,DDTYPE,YTIME)` | climate index (1) | 1 |

`i02ClimIdx` is written to `blabla.gdx` with all other symbols, so on and off runs
can be compared there.

## 4. Input files

Both are read only when `climFeedback == on`. Lookup order (first match wins):
`./<file>`, then `./data/<file>`, then the neutral template in
`modules/02_Industry/technology/templates/`. The file actually used is written to
the GAMS log.

* `iClimDegDays.csv`: rows `DDTYPE.region`, year columns, ratio of degree days to
  2023. Generated by OPEN-PROM → MAGICC → RIME (below). Missing or zero entries stay 1.
* `iClimShares.csv`: rows `region.subsector`, columns `HDD` (heating share) and
  `CDD` (cooling share). Source: IEA Energy End-uses and Efficiency Indicators.
  Only `HOU` and `SE` are used; everything else is 0.

The templates are neutral placeholders.

### Generating `iClimDegDays.csv`: OPEN-PROM → MAGICC → RIME

RIME is used as an external package, the same way MAGICC is used through
climate-assessment. Its repository stays unchanged, and all OPEN-PROM scripts are
in `scripts/tools`:

| Step | Script | Environment (WSL) |
|---|---|---|
| MAGICC: emissions → median GSAT | `runClimateModels.r` → climate-assessment `run_workflow.py` | `../climate-assessment/.venv` |
| RIME: GSAT → gridded degree days per year | `rimeMaps.py`, which calls RIME's `GMTPathway`, `RasterArray` and `map_transform_gwl_wrapper` | `../rime/.venv` |
| Degree days per OPEN-PROM region → ratios | `climDegreeDays.py` | `../rime/.venv` |

**Install once (WSL, from the OPEN-PROM root):**

```
bash scripts/tools/installClimateAssessmentToolWSL.sh   # MAGICC (tutorial 13)
bash scripts/tools/installRimeWSL.sh                    # RIME
```

`installRimeWSL.sh` does three things:
* clones RIME at a tested commit to `../rime`;
* creates `../rime/.venv` with Python 3.10 and the pinned packages of
  `scripts/tools/rime-requirements.txt` (RIME needs Python 3.10, and
  climate-assessment needs 3.11+, so they use separate environments);
* creates `../rime-data`.

**Run** the VS Code task **RUN CLIMATE EMULATOR** with `magicc`, the run folder
and `all`. From the OPEN-PROM root, the same command is:

```
Rscript scripts/tools/runClimateModels.r --model magicc --runFolder <run> --steps all
```

Outputs are written to `runs/<run>/EmissionsOutput-magicc/`:

| File | Content |
|---|---|
| `emissions_alloutput.xlsx`, `Global_Mean_Temperature.png` | MAGICC |
| `rime_maps_sdd_c_24p0.nc` | RIME degree-day maps (lat, lon, year) |
| `iClimDegDays.csv` | the OPEN-PROM input |
| `iClimDegDays_absolute.csv`, `iClimDegDays_diagnostics.png` | absolute degree days per region, ratio plot (for reporting) |

`--steps rime` reruns only RIME and the degree days on an existing MAGICC output.
Then copy `iClimDegDays.csv` (and `iClimShares.csv`) to `data/` and run
OPEN-PROM with `--climFeedback=on`.

**Data.** The impact data are the Climate Solutions Explorer maps
`cse_sdd_c_24p0_ssp2_<gwl>_abs.nc4`: cooling degree days with a 24 °C base, at
warming levels 1.2–3.5 °C (Werning et al. 2024, v1.1, doi:10.5281/zenodo.14524342,
CC BY 4.0). `rimeMaps.py` downloads them once from Zenodo (`energy.zip`, 19 MB)
into `../rime-data`. The Natural Earth country polygons are cached there too. The
region mapping is mrprom's `regionmappingOPDEV5.csv`, found automatically.

**Method.**
* **RIME maps:** each year's map is read at that year's median GSAT, interpolating
  between warming levels in 0.01 °C steps. RIME's own limits apply: temperatures
  between 1.2 and 3.5 °C, and a drawdown below the peak of at most 0.15 °C. In an
  overshoot run, the maps stop at the last year that passes the drawdown check,
  e.g. 2060.
* **Regional means:** countries are grouped into the 39 OPEN-PROM regions. Each
  0.5° cell counts with the fraction of it that lies in the region, from a 10×10
  sub-sampling, so small countries such as MLT and LUX are kept. Cells are weighted
  by SSP2 gridded population of each year (`climate_feedback.pop_grid`, ISIMIP
  `ssp2soc`); without that file, area weights are used.
* **Annual values:** linear between the 5-year RIME years. The last emulated value
  is held after the end of emulation.
* **Ratio:** `min(cap, 1 + (DD(t) − DD(2023)) / max(DD(2023), floor))`. It is
  exactly 1 in 2023 and equals `DD(t)/DD(2023)` wherever `DD(2023) ≥ floor`. The
  floor is 50 °C·days for CDD and 100 for HDD, and the cap is 3. The regions where
  the floor or cap acts are printed. At a 24 °C base, most of central and northern
  Europe has fewer than 50 CDD, so the floor damps the ratios there.
* **No heating degree days** exist in these data. HDD = 1, and only the cooling
  side of the feedback is active.

Settings in `config.json` (defaults in `config.template.json`):

```json
"paths": { "rime_path": "../rime", "rime_data_path": "../rime-data" },
"climate_feedback": { "ssp": "SSP2", "cdd_indicator": "sdd_c_24p0", "hdd_indicator": null,
                      "pop_grid": null, "regionmapping": null,
                      "floor_cdd": 50, "floor_hdd": 100, "cap": 3.0 }
```

## 5. Assumptions

* No adaptation: the response of demand to degree days does not change over time.
* Shares are fixed at their 2023 values.
* Air-conditioning uptake comes only through the existing income/activity
  elasticities. The CDD factor scales the cooling share. It does not add new AC
  ownership.
* The `legacy` Industry realization is not affected.
